# Agent + Workflow（自然语言编排）风险说明

> 更新时间：2026-02-13
> 
> 目标：识别“自然语言 -> DSL -> dry-run 校验 -> 正式执行”链路中的关键风险，给出可落地的缓解方案，作为上线与迭代依据。

## 1. 范围与前提

本文覆盖以下链路：

1. Agent 根据用户自然语言生成/修改 workflow DSL
2. 后端通过 dry-run 接口校验 DSL（结构、模板、执行条件）
3. 校验通过后创建/更新 workflow，并在飞书事件中执行

不覆盖 UI 画布设计与交互风险。

---

## 2. 风险分级标准

- **严重度（Severity）**
  - `S1`：导致错误写入/删除、业务中断、严重合规问题
  - `S2`：功能部分失效、通知错误、人工可恢复
  - `S3`：体验下降、排查成本增加
- **概率（Likelihood）**
  - `P1`：高概率（频繁出现）
  - `P2`：中概率（偶发）
  - `P3`：低概率（边界场景）

---

## 3. 风险清单（Risk Register）

| ID | 风险 | 严重度 | 概率 | 典型表现 | 当前状态 | 建议措施 |
|---|---|---|---|---|---|---|
| R1 | Agent 生成 DSL 语义偏差 | S1 | P2 | JSON 结构合法，但业务语义错误（字段/条件/动作不符合预期） | 已有 dry-run 基础能力 | 增加“DSL 白名单约束 + 失败回馈循环 + 人工确认门” |
| R2 | dry-run 与 live 执行不一致 | S1 | P2 | dry-run 通过，正式执行失败 | 已有 dry-run 路由 | 保证 dry-run/live 共用同一套插件与模板解析路径；建立一致性回归测试 |
| R3 | 字段映射漂移（改名/类型变更） | S1 | P2 | 工作流突然命中失败或条件误判 | 已有 field mapping registry | 增加字段映射刷新与告警；对关键字段使用 ID+Name 双校验 |
| R4 | 事件重复投递导致重复执行 | S1 | P2 | 同一记录被重复更新/重复通知 | 当前有内存去重 | 增加持久化幂等键（event_id + workflow_id + step_id） |
| R5 | 外部依赖网络抖动（Supabase/Feishu） | S2 | P1 | socket closed、请求超时、间歇失败 | 已有部分重试 | 区分可重试/不可重试错误；加入退避重试上限与死信记录 |
| R6 | 消息格式兼容性（换行/@用户） | S2 | P2 | 文本显示 `\n`、`@` 未生效、消息结构退化 | 已补充文档与部分实现 | 固化模板规范；增加 webhook 消息体回归样例（text/post 两种） |
| R7 | 安全边界不足（危险动作越权） | S1 | P3 | Agent 生成高风险动作并被执行 | 尚未系统化约束 | 引入动作白名单、scope 绑定校验、敏感动作二次确认 |
| R8 | 可观测性不足导致排查慢 | S3 | P2 | 只能看到底层日志，难以快速判断业务结果 | 已新增业务摘要日志 | 统一 traceId 贯穿，补充失败分类统计与告警阈值 |

---

## 4. 优先级建议（最小硬化清单）

### P0（建议优先完成）

1. **幂等持久化**
   - 在数据库记录 `(event_id, workflow_id, step_id)` 执行键
   - 重复事件直接跳过，避免重复副作用
2. **dry-run/live 一致性保障**
   - 明确共享执行引擎、模板解析与条件计算路径
   - 增加 10 条关键场景回归（创建/更新/删除、条件分支、模板插值）
3. **Agent 输出约束**
   - 固化 DSL schema 与动作白名单
   - dry-run 失败自动回馈修复，超过阈值转人工确认

### P1（建议随后完成）

1. 字段映射漂移告警（关键字段丢失/类型变化）
2. 外部依赖失败分级与死信队列
3. 通知消息格式回归样例库（换行、@用户、富文本）

---

## 5. 监控与验收建议

- **关键指标**
  - dry-run 通过率
  - live 执行成功率
  - 重试触发率与最终失败率
  - 重复事件拦截次数
- **验收门槛（建议）**
  - dry-run 与 live 一致性测试通过率 >= 95%
  - P0 风险均有“技术控制点 + 监控信号 + 回滚方案”
  - 关键链路失败可在 5 分钟内通过日志定位原因

---

## 6. 结论

当前系统已具备可用性，适合在受控范围内持续使用。

后续重点不是“功能堆叠”，而是围绕 **正确性、一致性、幂等性、可观测性** 做硬化，以降低规模化使用时的线上风险。
