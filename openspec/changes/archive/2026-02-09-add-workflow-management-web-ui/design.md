## Context

当前服务基于 Bun + Hono，后端已经提供完整的工作流 CRUD API（`/api/workflows`）并统一了响应结构（`code/message/data/meta`），同时具备 Swagger 文档（`/docs`）。

但在实际使用中，工作流配置仍依赖手写 JSON 与接口调试，存在以下问题：
- 配置学习成本高，业务侧难以直接上手。
- 触发条件、步骤、作用域（`table/global`）容易配置错误。
- 缺少可视化管理入口，不利于日常维护与排障。

约束与相关方：
- 约束：项目当前未引入前端框架构建链路（如 React/Vite）；应优先复用现有 Bun 运行方式。
- 约束：后端接口语义已确定，本次优先“前端消费接口”，避免改动核心执行引擎。
- 相关方：运营/业务配置人员（主要用户）、后端研发（维护接口一致性）、运维（部署与联调）。

## Goals / Non-Goals

**Goals:**
- 提供可在浏览器直接使用的工作流管理页面（列表、创建、编辑、删除、启停）。
- 让用户无需阅读 API 文档也可完成常见工作流配置。
- 在前端对关键字段（名称、scope、trigger、steps）进行即时校验，降低无效请求。
- 与现有后端 API 保持一致，统一展示后端返回的错误码与错误信息。

**Non-Goals:**
- 不在本次引入复杂前端工程化体系（如 SPA 构建、状态管理框架）。
- 不重写工作流 DSL 语义与执行引擎（condition/action 插件不在本次范围）。
- 不新增权限系统与账号体系（沿用当前服务暴露方式）。
- 不在本次做高级功能（版本历史、可视化流程编排器、拖拽式 DSL 编辑）。

## Decisions

### 决策 1：采用“服务端静态页面 + 原生 JS”实现首版管理界面

**方案**
- 在后端服务中新增页面路由（例如 `/ui/workflows`），返回静态 HTML。
- 页面内使用原生 JavaScript 调用现有 `/api/workflows` 接口。
- 静态资源放在项目内可维护目录（如 `src/ui/`），由 Bun/Hono 提供访问。

**理由**
- 与现有技术栈最一致，落地快、依赖少。
- 不引入额外构建工具，降低部署复杂度。
- 适合当前“管理台 MVP”阶段。

**备选方案与取舍**
- 备选 A：引入 React/Vue + Vite。
  - 优点：组件化更强；缺点：改造成本高、需要新增构建与发布链路。
- 备选 B：单独部署前端项目。
  - 优点：边界清晰；缺点：多仓或多服务运维复杂度上升。

### 决策 2：采用“列表摘要 + 详情编辑”双模型

**方案**
- 列表页使用 `GET /api/workflows`，仅展示摘要（名称、状态、scope、更新时间）。
- 进入编辑时调用 `GET /api/workflows/{id}` 获取完整 `config`。
- 创建/更新提交时使用完整 payload（`name/config/scope/isActive`）。

**理由**
- 与现有接口设计一致（列表与详情分离），减少首屏数据量。
- 编辑页按需拉取详情，避免不必要的 config 传输。

**备选方案与取舍**
- 备选：列表直接返回完整 config。
  - 缺点：数据冗余、列表性能变差，且不利于后续扩展。

### 决策 3：表单分层展示 DSL，优先“可用性”而非“完全可视化”

**方案**
- 基础字段（名称、启用状态、scope）使用结构化表单控件。
- `trigger` 与 `steps` 先采用 JSON 编辑区 + 示例模板 + 语法校验提示。
- 提交前执行前端 JSON 解析与必填校验；服务端错误原样展示。

**理由**
- 当前 DSL 已存在，直接用 JSON 可最快复用后端能力。
- 在可控成本下提供“比 Swagger 更友好”的配置体验。

**备选方案与取舍**
- 备选：完整拖拽式流程编排器。
  - 缺点：实现复杂，短期难以稳定交付。

### 决策 4：错误与反馈统一遵循后端 envelope

**方案**
- 前端统一解析响应：
  - 成功：显示 `message` 并刷新目标数据。
  - 失败：显示 `code + message`，必要时附 `details`。
- 对常见错误（例如 `WORKFLOW_NOT_FOUND`、`WORKFLOW_CREATE_FAILED`）给出更友好中文提示。

**理由**
- 保持前后端契约一致，便于定位问题。
- 降低用户对技术错误信息的理解成本。

## Risks / Trade-offs

- [风险] JSON 编辑仍可能误配 DSL → 缓解：提供默认模板、字段示例与实时语法校验。
- [风险] 单页静态实现在功能增多后可维护性下降 → 缓解：按模块拆分脚本（API 层、视图层、状态层）并预留升级到框架的边界。
- [风险] 与后端字段不一致导致提交失败 → 缓解：复用 OpenAPI schema 约束命名，联调时覆盖 CRUD 全流程。
- [权衡] 不引入前端框架可快速交付，但中长期扩展性一般 → 缓解：先完成 MVP，后续视复杂度再演进到工程化前端。

## Migration Plan

1. 页面接入
   - 新增 UI 路由与静态页面资源，确保服务启动后可访问工作流管理页面。
2. 数据联通
   - 对接 `GET/POST/PUT/DELETE /api/workflows`，完成列表、创建、编辑、删除闭环。
3. 交互增强
   - 增加表单校验、错误提示、加载状态与成功反馈。
4. 文档更新
   - 在 README/接口文档中补充页面访问路径与使用说明。
5. 验收
   - 手工验证完整 CRUD 与 scope 配置流程，确认与 Swagger 行为一致。

**Rollback Strategy**
- 保留后端 API 不变；若 UI 出现问题，可临时下线页面路由，仅保留 API 与 Swagger 能力。
- UI 代码按独立目录管理，回滚时可按文件粒度快速撤销。

## Open Questions

- 页面入口路径最终是否固定为 `/ui/workflows`，还是放在 `/admin/workflows`？
- 首版是否需要“克隆工作流”能力（基于现有 workflow 快速新建）？
- 是否需要在列表提供按 `scope.type` 与 `isActive` 的前端筛选控件？
- 后续是否需要支持非技术用户的“表单化步骤编辑器”（替代 JSON 输入）？
