## Context

当前 workflow 运行时已经完成 table-only 路由收敛，但事件类型过滤仍主要依赖 DSL 内部字段，缺少结构化的一等路由字段，导致候选命中与执行语义存在分离。与此同时，现有执行引擎以线性 steps 顺序执行为主，虽然 DSL 存在 `next` 字段，但尚未形成可校验、可视化友好的分支控制流语义，无法直接支撑业务人员在 Web 端做流程编排。

约束：
- 现网已有 workflow 数据，必须兼容老配置并提供平滑迁移。
- API 与 UI 已面向 table scope 发布，新增能力不能破坏现有入参。
- 运行时不能引入高复杂度依赖，优先在现有引擎与数据库结构内迭代。

相关方：
- 业务配置人员：希望在页面中按“触发范围 + 分支流程”直观配置。
- 后端研发：需要明确路由与 DSL 的单一语义，降低故障定位成本。
- 运维与测试：需要迁移可观测、可回滚、可验收。

## Goals / Non-Goals

**Goals:**
- 将 workflow 触发范围从“table”升级为“table + optional eventTypes”，并支持结构化路由查询。
- 引入分支型 DSL（DAG 语义）以表达 `if/else` 与节点跳转，支持复杂业务流程。
- 保持对现有线性 DSL 和未配置 eventTypes 的 workflow 的兼容执行。
- 统一 API/UI/运行时语义，保证配置、存储、执行三个层面一致。

**Non-Goals:**
- 不在本次实现完整图形化拖拽编排器（先提供 JSON 能力与基础 UI 承载）。
- 不引入循环流程（仅支持有向无环图）。
- 不在本次重构所有插件实现细节，仅定义控制流与路由匹配框架。
- 不在本次清理历史 `rules` 领域模型（沿用既有清理路径）。

## Decisions

### 决策 1：将 `eventTypes` 提升为 scope 概念，但保持可选

**方案**
- `scope` 继续必填 `type=table + appToken + tableId`。
- 新增可选 `scope.eventTypes`（数组）。
- 语义：
  - 未配置/空数组 = 该表所有事件可触发。
  - 配置后 = 仅匹配指定事件（`record_created`/`record_updated`/`record_deleted`）。

**理由**
- 与“触发范围”认知一致，降低业务配置成本。
- 可选设计兼容老 workflow，避免一次性破坏升级。

**备选方案与取舍**
- 备选 A：仅保留在 `trigger.config.action` 中，不升维到 scope。
  - 缺点：路由字段与 scope 语义分裂，难做数据库索引优化。
- 备选 B：将 eventTypes 设为必填。
  - 缺点：对现存数据不兼容，迁移与使用门槛变高。

### 决策 2：新增结构化事件路由字段并作为候选查询主路径

**方案**
- 在 `workflows` 表新增（或强化）结构化字段（例如 `trigger_actions text[]`）。
- 候选查询按 `is_active + scope_type + app_token + table_id` 过滤后，再由数据库层执行 eventType 命中判断。
- 保留运行时兜底过滤，防止脏数据造成误执行。

**理由**
- 候选集更小，减少“命中后跳过”的噪声日志。
- 路由逻辑可观测、可索引、可审计。

**备选方案与取舍**
- 备选：仅在内存中解析 DSL 后过滤 eventType。
  - 缺点：放大运行时负担，无法利用数据库索引。

### 决策 3：定义“DSL 描述 DAG”的控制流模型，兼容线性模式

**方案**
- 节点级控制字段：
  - condition 节点支持 `onTrue`、`onFalse`。
  - action/其他节点支持 `next`。
- 执行入口优先按图遍历；未提供跳转字段时退化为原顺序执行。
- 增加 DAG 校验：节点唯一性、引用有效性、无环。

**理由**
- 既满足 if/else 分支能力，又保持老配置零迁移可运行。
- 便于后续 Web 端从“列表编辑”平滑升级到“图编辑”。

**备选方案与取舍**
- 备选 A：直接抛弃数组 steps，改为纯 graph 对象。
  - 缺点：破坏性强，迁移成本高。
- 备选 B：继续线性执行，用多 workflow 拼接分支。
  - 缺点：业务语义分散，调试复杂。

### 决策 4：配置冲突采用“显式失败”策略

**方案**
- 当 `scope.eventTypes` 与 `trigger.config.action/actions` 同时存在且语义不一致时，API 返回 400。
- 当只存在一侧时，服务端在写入时自动规范化并同步另一侧。

**理由**
- 防止出现“看起来配置了，但运行时按另一套逻辑执行”的隐性故障。

**备选方案与取舍**
- 备选：总是以某一侧覆盖另一侧。
  - 缺点：容易产生静默数据变更，排障困难。

## Risks / Trade-offs

- [风险] DAG 引入后配置复杂度上升 → 缓解：先提供模板与校验提示，并保留线性默认路径。
- [风险] 历史数据 event 语义不规范（`add/update/remove` 混用）→ 缓解：统一归一化字典并在迁移报告中输出异常项。
- [风险] 路由字段与 DSL 双写可能短期不一致 → 缓解：以 API 层单一规范化函数为写入口，并加一致性测试。
- [权衡] 保留运行时兜底过滤会增加少量重复判断，但能显著提升迁移期间安全性。

## Migration Plan

1. 数据模型阶段
   - 为 `workflows` 新增/完善事件路由字段与索引。
   - 提供回填脚本：从 `trigger.config.action/actions` 推导结构化字段。
2. API 与模型阶段
   - 扩展 scope schema（新增可选 `eventTypes`）。
   - 引入 scope/trigger 双向规范化与冲突校验。
3. 运行时阶段
   - 数据库候选查询增加 eventType 过滤。
   - 保留运行时兜底过滤与告警日志。
4. DSL 引擎阶段
   - 增加 DAG 控制流执行器与校验器。
   - 保持线性 DSL 兼容执行。
5. UI 阶段
   - 增加 eventTypes 配置控件与 DSL 分支模板。
   - 保持旧工作流可编辑、可保存。
6. 验收与上线
   - 执行兼容回归（旧 workflow/新 workflow/混合场景）。
   - 验证日志、路由命中、分支执行正确性。

**Rollback Strategy**
- 路由字段与分支执行均采用向后兼容策略，可通过代码回退恢复旧线性路径。
- 保留迁移前 workflow 快照与回填报告，必要时恢复旧配置。

## Open Questions

- `eventTypes` 是否允许未来扩展到更细粒度（如字段级变更事件）并保持向后兼容？
