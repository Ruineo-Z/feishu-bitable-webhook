## Context

当前后端事件处理链路仍为“双轨并行”：`workflow` 新引擎与 `rules` 旧引擎同时执行，导致触发语义分散、故障定位困难、迁移边界不清。另一方面，飞书事件中字段以 `field_id` 形式出现，而多维表格动作配置与检索参数常以字段名为主，若无统一映射层，工作流在跨表写入、条件查询等场景会出现不稳定行为。

本次变更需要在不牺牲可观测性的前提下，完成“运行时主链路收敛 + 映射能力独立化”的架构调整。

约束与相关方：
- 约束：现网已有 `rules`、`bitables`、`workflows` 历史数据，切换必须可回滚。
- 约束：飞书事件与 SDK 的字段表达差异客观存在，不能仅靠约定规避。
- 相关方：业务配置人员（工作流可用性）、后端研发（迁移复杂度）、运维（稳定性与回滚）。

## Goals / Non-Goals

**Goals:**
- 统一实时执行入口为 workflow-only，消除双引擎并行带来的不确定性。
- 提供独立字段映射能力，稳定支撑 `field_id` 与字段名互转。
- 补齐 workflow 插件能力，使旧 rules 常用动作可在 workflow 中等价表达。
- 建立分阶段迁移方案，确保上线可观测、可回滚。

**Non-Goals:**
- 不在本次重构整个工作流 DSL 语法。
- 不引入新的外部中间件（如 Redis、消息队列）作为前置依赖。
- 不在本次实现前端高级编排器能力。
- 不要求一次性物理删除旧表，先完成运行时职责迁移。

## Decisions

### 决策 1：运行时切换为 workflow-only，rules 退出实时主链路

**方案**
- 事件接收后只执行 workflow scope 路由与 workflow engine。
- 旧 rules 链路停止参与实时事件执行。

**理由**
- 单一执行模型更易理解、调试与扩展。
- 避免同一事件在两条链路重复触发动作。

**备选方案与取舍**
- 备选：继续双轨并行并做去重。
  - 缺点：去重语义复杂，长期维护成本更高。

### 决策 2：将字段映射能力独立为专用 registry（而非继续绑在 bitables）

**方案**
- 以 `app_token + table_id + field_id` 作为映射主键，维护 `field_name` 与更新时间。
- 通过字段变更事件增量维护，提供按表全量刷新能力。

**理由**
- 把“映射能力”与“表连接配置/白名单”解耦，避免职责混杂。
- 直接服务 workflow 运行时，不依赖旧 bitables 领域模型。

**备选方案与取舍**
- 备选 A：继续复用 `bitables.field_mappings`。
  - 缺点：难以完成 workflow-only，且遗留模型耦合持续存在。
- 备选 B：每次动作实时拉字段列表，不落库。
  - 缺点：性能与稳定性不可控，且增加飞书 API 压力。

### 决策 3：补齐 workflow 动作插件能力，覆盖旧 rules 主能力

**方案**
- 在 workflow 插件体系中补充 `create_record`、`delete_record`、`query_records`（以及必要批量能力）。
- 插件统一消费映射 registry，支持以事件字段动态构建动作参数。

**理由**
- 先补齐能力再下线旧链路，降低迁移风险。
- 把动作演进集中到 workflow 插件层，减少引擎间重复实现。

**备选方案与取舍**
- 备选：短期继续复用旧 actions 调用路径。
  - 缺点：技术债延续，难以形成清晰边界。

### 决策 4：采用“先兼容、后切换、再清理”的迁移路径

**方案**
- Phase 1：引入映射 registry，并进行双写/双读兼容。
- Phase 2：切换实时执行到 workflow-only，并启用新映射读取路径。
- Phase 3：下线 bitables 运行时依赖与旧接口，保留必要数据窗口后再清理。

**理由**
- 分阶段降低发布冲击，保留可回退抓手。

## Risks / Trade-offs

- [风险] 映射缺失导致动作字段解析失败 → 缓解：提供按表刷新接口 + 启动/定时自愈刷新 + 缺失告警。
- [风险] workflow 插件能力未完全覆盖旧动作 → 缓解：切换前建立能力对照清单与灰度验证清单。
- [风险] 切换窗口出现执行差异 → 缓解：关键路径打点（候选数、命中率、失败码）并保留回滚开关。
- [权衡] 先保留旧表增加短期维护负担，但可显著降低一次性大迁移风险。

## Migration Plan

1. 数据模型准备
   - 新增字段映射 registry 表与索引。
   - 提供 DAO 与刷新接口。
2. 能力补齐
   - 实现 workflow 动作插件补齐与映射接入。
3. 双轨验证
   - 在预发布环境比对 workflow-only 与现有结果一致性。
4. 主链路切换
   - 生产启用 workflow-only 实时执行，停用 rules 实时执行入口。
5. 清理收敛
   - 下线旧 bitables 刷新接口与运行时强依赖。

**Rollback Strategy**
- 保留切换开关，可快速回退到旧实时链路（短窗口内）。
- 映射 registry 与旧存储并存一段时间，避免单点回滚失败。

## Open Questions

- workflow 动作插件是否在本次同步补齐批量能力（batch create/update/delete）？
- 旧 rules 的生命周期策略是“只读保留”还是“迁移后归档清理”？
- 是否需要为 workflow-only 切换增加运行时 feature flag 与环境分级策略？
