## Context

当前 workflow 管理页基于静态 `index.html + app.js + view.js` 直出，核心配置依赖 JSON 文本框输入。该实现对研发调试友好，但对业务角色不友好，主要问题包括：

- 业务用户无法安全构造 DSL，常见错误只能在提交后由后端返回。
- 表单信息与 DSL 结构耦合，缺少结构化引导与步骤化反馈。
- 当前前端非工程化子项目，不利于后续扩展（可视化步骤编辑、分支管理、字段提示、配置复用）。

项目尚未上生产，允许替换现有 `/ui/workflows` 页面实现，并在当前仓库内引入前端子项目以降低联调成本。

## Goals / Non-Goals

**Goals:**

- 在当前仓库内新增 React 子项目（`web/workflow-studio`），作为 workflow 管理台的唯一前端实现。
- 提供“可视化配置优先”的创建/编辑流程：触发器、作用域、步骤、分支、动作由表单驱动。
- 保留“高级模式”查看/编辑 DSL JSON，兼容研发排障场景。
- 保持现有工作流 API 契约不变（`/api/workflows` 系列），通过前端映射完成 UI 模型与 DSL 互转。
- 用明确反馈机制降低误操作：提交中状态、字段校验、分区错误提示。

**Non-Goals:**

- 不改造 workflow 执行引擎行为（条件求值、插件执行、事件路由保持现状）。
- 不在本次引入复杂拖拽 DAG 画布（先落地表单化步骤/分支编辑）。
- 不引入新的后端存储模型或 workflow API 版本。

## Decisions

### Decision 1：采用“同仓 React 子项目”而非独立仓

- **选择**：在当前仓库新增 `web/workflow-studio`（Vite + React + TypeScript）。
- **原因**：
  - 当前阶段需求高频变更，同仓更利于 API 与 UI 协同演进。
  - 降低跨仓发布与契约漂移风险。
  - 保留后续拆仓可能（通过 build 产物与路由边界隔离）。
- **备选方案**：
  - 独立前端仓库：发布隔离更好，但当前联调成本高。
  - 继续静态页面：短期开发快，长期复杂度不可控。

### Decision 2：采用“表单模型 -> DSL 生成”的双向架构

- **选择**：前端维护结构化 `FormModel`，提交前生成 DSL；编辑已有 workflow 时将 DSL 反解析回 `FormModel`。
- **原因**：
  - 业务用户无需直接操作 JSON。
  - 便于分区校验、错误定位和 UI 引导。
  - 可持续扩展更多步骤类型与字段模板。
- **备选方案**：
  - 只做 JSON 编辑器增强：仍不能解决业务用户可用性问题。
  - 完全后端生成 DSL：会让前端状态不可控，交互迭代慢。

### Decision 3：路由切换策略采用“直接替换入口 + 保留回退开关”

- **选择**：将 `/ui/workflows` 指向 React build 产物；保留环境开关（如 `WORKFLOW_UI_LEGACY=true`）可临时回退旧静态页。
- **原因**：
  - 用户已接受替换现有页面，不需要双入口长期并行。
  - 提供最小回退机制，避免上线风险。
- **备选方案**：
  - 长期双入口并行：维护成本高、行为分叉。

### Decision 4：首期交互范围聚焦“可用优先”

- **选择**：首期实现列表、筛选、分页、可视化创建/编辑、删除确认、高级 JSON 模式。
- **原因**：
  - 快速替代不可用环节（手写 JSON）。
  - 保障与现有 API 完整可联调。
- **备选方案**：
  - 一次性上拖拽画布：实现周期长，验证路径慢。

### Decision 5：页面视觉语言采用“浅色科技感（Halo 金青）+ 可控动效”

- **选择**：
  - 首版默认主题采用 `Halo 金青`（浅色、科技感、非传统企业后台风格）。
  - 保留主题档位能力（Aero/Quantum/黑金实验档），但生产默认保持 `Halo 金青`。
  - 动效策略采用“少量关键动效 + 可关闭”，避免全局炫技。
- **原因**：
  - 满足“更有生命力、但不走暗黑”的明确偏好。
  - 在可读性与科技感之间平衡，降低业务用户认知压力。
  - 后续可通过主题 token 迭代，不影响业务逻辑。
- **备选方案**：
  - 传统浅色企业风：稳定但辨识度不足。
  - 全暗色赛博风：科技感强但不符合当前审美偏好。

## Risks / Trade-offs

- **[Risk] DSL 反解析覆盖不全导致编辑回填异常** → **Mitigation**：定义受支持 DSL 子集；超出子集时自动切换到高级模式并给出提示。
- **[Risk] 新增前端子项目增加构建复杂度** → **Mitigation**：将构建命令标准化到 `package.json`，并在后端路由层统一静态资源入口。
- **[Risk] 替换入口后用户习惯迁移成本** → **Mitigation**：保留“高级模式”与字段说明文案，降低心智切换成本。
- **[Risk] 与现有 API 的字段命名不一致** → **Mitigation**：在前端引入 API adapter 层，统一入参与出参映射。

## Migration Plan

1. 初始化 `web/workflow-studio` 子项目与基础工程（Vite + React + TS + 基础样式体系）。
2. 构建 `api client` 与 `workflow adapter`（FormModel <-> DSL）。
3. 先落地列表页（查询、筛选、分页、删除）。
4. 落地可视化编辑页（基础信息、触发范围、步骤配置、分支设置）。
5. 增加高级 JSON 模式与模式切换校验。
6. 集成构建产物到后端 `/ui/workflows` 路由。
7. 验证回退开关有效，完成切换。

## Open Questions

- 是否首期就支持“步骤模板库”（如常用 A->B 同步模板），还是第二阶段再加？
- 高级模式是否允许“仅查看不编辑”，以降低误改风险？
- 是否需要在 UI 里提供“模拟校验”（不落库，只跑 DSL 校验）按钮？
