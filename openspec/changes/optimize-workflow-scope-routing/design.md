## Context

当前工作流事件处理链路在 `src/lark.ts` 中采用“全量加载 active workflows（`workflowsDb.findActive`）→ 逐个内存过滤 trigger”模式。该模式在工作流数量增加时会带来两类问题：

1. 匹配性能随工作流数量线性增长，事件高峰时处理延迟不可控。
2. 绑定条件（`app_token`、`table_id`）在现有模型中是可选的，容易出现隐式全局匹配与误触发。

同时，系统已有运行中的历史工作流数据，不能通过一次性破坏性变更切换到新模型；需要兼容迁移与可回滚方案。

约束与相关方：
- 约束：保持现有事件解析与步骤执行引擎（condition/action 插件）可复用，避免大规模重写。
- 约束：数据库为 Supabase/Postgres，变更应优先通过可索引字段实现快速路由。
- 相关方：业务配置方（配置工作流）、运维/研发（保障稳定）、下游系统（依赖触发一致性）。

## Goals / Non-Goals

**Goals:**
- 将“工作流作用域绑定”从隐式规则升级为显式模型，默认绑定到 `app_token + table_id`。
- 将匹配路径重构为“先路由、后条件”，实现事件到候选工作流的快速定位。
- 保持与现有工作流配置的兼容性，提供平滑迁移与观测能力。
- 为后续能力（如按 action 粒度路由、灰度发布）预留数据结构扩展点。

**Non-Goals:**
- 不在本次变更重写步骤执行引擎（不引入 DAG/并行/重试语义改造）。
- 不合并旧规则引擎（rules）与新工作流引擎（workflows）的业务语义。
- 不在本次引入新的外部基础设施（如 Redis）作为路由主依赖。

## Decisions

### 决策 1：引入显式作用域模型（Scope）

**方案**
- 为工作流定义显式作用域：
  - `scope_type = table`：绑定 `app_token + table_id`。
  - `scope_type = global`：显式全局工作流。
- 对于 `table` 作用域，`app_token` 与 `table_id` 为必填。
- 对于 `global` 作用域，`app_token` 与 `table_id` 为空。

**理由**
- 显式模型优于“字段缺失即全局”的隐式约定，降低误触发风险。
- 将作用域字段从 JSON config 中抽取到结构化列，才能建立高效索引。

**备选方案与取舍**
- 备选 A：继续仅使用 `config.trigger` 的 JSON 字段过滤。
  - 问题：查询路径难索引、性能不可预测。
- 备选 B：仅在内存构建路由 map，不改数据模型。
  - 问题：进程重启冷启动慢，配置变更同步复杂。

### 决策 2：匹配流程改为“两阶段路由”

**方案**
1. 阶段一（路由筛选）：按 `is_active + scope` 查询候选工作流。
2. 阶段二（业务判断）：仅对候选工作流执行现有条件评估与步骤执行。

**理由**
- 将 O(N) 全量扫描缩减为 O(K) 候选集处理（K << N）。
- 保持现有条件/动作插件稳定，改动集中在“查找层”。

**备选方案与取舍**
- 备选：直接在数据库层表达完整条件判断。
  - 问题：表达复杂、可维护性差，且难以复用现有 ConditionEvaluator。

### 决策 3：查询策略同时支持“表级 + 显式全局”

**方案**
- 事件到达时，候选集由以下两类合并：
  - 表级命中：`scope_type=table AND app_token=? AND table_id=?`
  - 全局命中：`scope_type=global`
- 后续可扩展可选 `trigger_action` 字段用于进一步缩小候选集。

**理由**
- 兼顾默认强绑定与少量全局场景（平台级通知、审计等）。
- 通过显式全局声明保障可读性与可控性。

### 决策 4：采用“兼容迁移 + 分阶段收敛”的变更策略

**方案**
- Phase 1（兼容期）：
  - 新建/更新接口接受新 scope 字段。
  - 对历史数据按旧 `config.trigger.config` 自动回填 scope。
- Phase 2（收敛期）：
  - 管控台/API 对新写入默认要求 table 绑定。
  - 隐式全局模式仅保留只读兼容，不再推荐。
- Phase 3（稳定期）：
  - 统一以显式 scope 为准，老字段只做回溯兼容。

**理由**
- 降低一次性切换风险，避免影响线上已有自动化流程。

## Risks / Trade-offs

- [风险] 历史工作流自动回填 scope 可能与业务预期不一致 → **缓解**：迁移脚本输出审计清单（哪些被判定为 global/table），并支持人工复核。
- [风险] 同时命中 table/global 可能导致重复或超预期执行 → **缓解**：在运行日志中新增路由命中来源标记（table/global），并提供全局工作流数量告警。
- [风险] 查询字段增多导致接口写入复杂度上升 → **缓解**：在 API 层做统一校验与默认化，减少调用方心智负担。
- [权衡] 保留全局工作流能力提升灵活性，但增加误配置面 → **缓解**：要求显式声明并在文档中标注高风险配置。

## Migration Plan

1. 数据库层
   - 为 `workflows` 增加 `scope_type`、`app_token`、`table_id`（以及必要索引）。
2. 数据回填
   - 读取历史 `config.trigger.config`：
     - 若存在 `app_token + table_id` → 回填为 `table`。
     - 否则回填为 `global`（并记录审计日志）。
3. 读路径切换
   - 事件路由查询切换到新字段（保留兼容兜底，限过渡期使用）。
4. 写路径切换
   - 工作流创建/更新接口接入 scope 校验与默认策略。
5. 观测与验收
   - 监控候选数量、匹配耗时、触发成功率；对异常增长设置告警。

**Rollback Strategy**
- 代码回滚：读路径退回旧全量扫描逻辑。
- 数据回滚：新增列可保留不影响旧逻辑；如需彻底回退，可停用新索引与新校验入口。

## Open Questions

- 是否在本次就引入 `trigger_action` 作为一等路由字段，还是先保持在条件层？
- 全局工作流是否需要配额/审批机制（例如每个环境最多 N 条）？
- 与旧规则引擎并行执行时，是否需要统一去重语义避免双引擎重复动作？
- API 层对 scope 的最终外露形态是顶层字段，还是保留在 config 下的逻辑分层？
